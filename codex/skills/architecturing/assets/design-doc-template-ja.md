# [Design Doc] 設計の題名

> **作業用 Draft**。調査・比較・試作と執筆を行き来するためのテンプレートです。
>
> - 見出し・小見出し、または関連する複数の節を作業単位にします。見出しは分割・統合・並べ替えできます。
> - 作成時は既知の背景、目的、見出しと執筆ガイドから始め、仮案や未整理の意見を書き込みません。それらは設計ループの中で扱い、探索や検証の結果を整理して文書に反映します。
> - AI が文書へ書き込む前に、対象箇所の草案または差分を提示し、書き込みの確認を得ます。確認済みの文章や編集には、再確認を求めません。
> - 試作用コードの作成・変更は、人間と AI のどちらが担当しても構いません。
> - 探索では箇条書き、図、疑似コード、書きかけの文章も使えます。文書には整理した結果を記載し、確認済みの事実、未決事項、採用した判断を区別します。
> - 「議論後にここを書く」などの執筆支援文は、引用ブロックや明確な注記を使い、設計本文と見分けられる形にします。
>
> 各節の案内は執筆中の補助です。すべてに回答する必要はありません。
> 最終化するときは不要な案内や空欄を除き、理由、根拠と限界、合意した保留を残します。重要な未決事項は、解消するか、影響を含めて保留を合意してから最終承認へ進みます。

## Context and scope

> **書くこと**：誰が何をしたいのか、現在どこに問題や必要性があるのか、この設計が扱う範囲。要件・仕様・確定済みの制約は原本を参照できるようにします。
>
> **書き始め方**：共有済みの目的や事実は AI が整理できます。既存の仕組みと今回の変更範囲を短くつなぎ、不明な背景をもっともらしく補わずに残します。採用予定の技術や仕組みを要件と混同しません。

### Goals

> **書くこと**：この設計で実現したい、利用者や呼び出し側から確認できる成果。
>
> **書き始め方**：「何ができるようになるか」「どの条件なら完了と判断できるか」を箇条書きにします。数値が必要なら根拠を確認し、未確認の目標値は提案として扱います。

### Non-goals

> **書くこと**：関連はするが、今回は扱わない成果や範囲。
>
> **書き始め方**：境界が曖昧になりそうなものを挙げます。実現が難しい要件を、設計上の都合だけでここへ移しません。

## Overview

> **書くこと**：全体の中心となる考え方、主要な構成要素と責務、その間を通る代表的な処理。
>
> **書き始め方**：作成時はこの案内を残し、仮の全体図で本文を埋めません。設計ループで検討した構造を整理できたら、何が既存で何を変えるのか、どの境界が未決なのかを説明します。後の節で案を選んだら、この全体像にも反映します。
> 構造図では責務と依存関係、処理の図では実行順やデータの受け渡しを示し、矢印の意味を説明します。配置が読みにくいフローチャートは ASCII 図でも構いません。

## Detailed design

> **書くこと**：Overview の方針を成立させる重要な境界、仕組み、契約と、その選択理由。
>
> **書き始め方**：冒頭で、ここから何を決めるのかを短く説明します。以下の小見出しは出発点です。対象に合う具体的な論点へ変え、必要な節を追加・統合します。全体を完成させてから書き始める必要はありません。

### モジュール構造と API の所有者

> **書くこと**：主要なモジュール・パッケージの親子関係、責務、対応するファイルやディレクトリ。各 API の所有者、利用者、公開範囲、利用・再公開経路、ソースコードの依存方向。
>
> **書き始め方**：設計ループで境界の案を比較し、整理した構造を関係する範囲の tree と責務の説明にします。Rust なら親を定義する `module_name.rs` と子を定義する `module_name/child.rs` を区別し、定義の配置と公開 API の所有者も分けて示します。
> 採用した境界の理由と、設計として固定する関係・パスを説明します。実装時に自由に変えられる補助関数まで列挙する必要はありません。

### モジュール API と主要な値・状態

> **書くこと**：モジュールの役割と利用者、API の所有者と利用経路。重要な値や状態、その関係、所有者と生存期間、守る条件。主要 API の操作と保証、呼び出し側の責任、この形を選んだ理由。
>
> **書き始め方**：モジュールごとに、何を引き受けて何を利用側に残すかから書きます。主要な型・操作の短い宣言を置き、値の意味、所有者や生存期間、各戻り値が意味することを近くで説明します。必要なら関係図や表を使います。
>
> 代表的な利用の流れを追い、宣言だけでは分からない順序、失敗時の対応、資源解放などを補います。役割・型と操作・利用の流れ・保証と責任・選択理由をつなげますが、すべてを固定の小見出しにする必要はありません。
>
> trait・interface を採用する境界なら、その重要な宣言部分を示します。具体型やモジュール関数なら、その公開操作を示します。文書のためだけに trait を導入せず、説明用スケッチと実装が守る契約を区別します。
>
> 状態の持ち方、初期化・終了、失敗条件や返す値の所有権が未決なら、設計上の論点として残します。仮の型名やエラー名を付けただけで、契約が決まったことにはしません。

### 主要フローと失敗・終了時の振る舞い

> **書くこと**：受付から完了までの経路、条件による分岐、順序や並行実行の保証。失敗・取り消し・終了時に誰が何をするか。
>
> **書き始め方**：具体的な一件の処理を追い、分岐や順序をフロー・シーケンス図、疑似コードで書きます。必要なら試作用コードの入力や順序を変えて確かめます。
> 資源を扱う場合は、表示や利用をやめる条件だけでなく、誰がいつ解放するかも追います。構造上の依存方向と、実行時の通知・受け渡しを混同しません。

### 対象に固有の設計論点

> **書くこと**：ここまでの節で扱いきれない、重要なアルゴリズム、保存方式、境界などの選択。この小見出しを実際の論点に置き換えるか、不要なら除きます。
>
> **書き始め方**：案や未整理の意見は設計ループで扱い、比較した条件、試した結果、今の判断と理由、未決事項を整理して記載します。調べただけの情報と、実際に観察した結果を区別します。
> 新しい前提や保証が必要になったら、未決の論点として調査・比較・試作へ戻します。

## Cross-cutting concerns

> **書くこと**：この設計に関わる性能、資源、安全性、運用、移行などの影響と対応。該当する懸念を小見出しにして、設計固有の理由を説明します。
>
> **書き始め方**：主要フローや境界を見直し、複数の節にまたがる影響を拾います。すべての分野を埋めるチェックリストにはしません。

### 検証方針と残っている不確実性

> **書くこと**：設計上の保証を確かめる条件や観察点、重要な試作結果とその限界、実装後に検証すること。合意した保留は、その影響も含めて残します。
>
> **書き始め方**：試した条件・実際の観察・そこから言えることを分けて記録し、必要な資料やログを参照します。未実行の実験を実施済みとは書かず、限定的な試作を本番の正しさや性能の証明として扱いません。
> 他の節に既に書いた結果は参照し、同じ内容を二重に更新しないようにします。

## Alternatives considered

> **書くこと**：実際に検討した有力な別案、その利点、採用しなかった理由、採用案で引き受ける負担。
>
> **書き始め方**：比較・試作のメモから、別案ごとに小見出しを作ります。検討していない案や却下理由を AI に補わせず、意味のある別案がなければ、その旨を短く書きます。
> 共通の比較軸があれば表を使えます。本文と表へ同じ説明を繰り返さず、選んだ理由が追える形にまとめます。
