# Requirements: Architecturing の命名と Draft の作成方針

- Date: 2026-11-05
- Updated: 2026-11-06
- Status: Aligned。初期 Draft を元に共同設計へ進むことと、2026-11-06 に AI の非迎合・思考支援・質問や事前提出を義務化しない三点を明記することをユーザーが確認。
- Source: 2026-11-05 から 2026-11-06 の本セッションでのユーザーの説明と追加依頼。

## 背景と目的

Design Doc を軸に、エンジニアと AI が構造を共有し、共同で設計を組み立てる
方法を `Architecturing` と呼ぶ。エンジニアは自身の考えや別案、システムや文書の
構造への意見を持ち寄る。AI も調査、案、草案などを通じて共同設計に参加する。
構造を共同で作り上げていく感覚を込め、`Architecting` という候補に対し、
あえて `turing` を含む `Architecturing` という綴りを選ぶ。

この方法の説明を README に加え、Design Doc を成果物とする既存の設計スキルの
改名として整理する。併せて、Draft 作成時に仮案などを書き込まないよう、指示を追加する。
エンジニア側の心構えだけに依存せず、自身の考えを持ち寄れるよう AI が支援する
方針を、スキルへの指示として明確にする。
変更に先立ち、この内容自体を Design Doc で設計する。

## 要求と保持する性質

- 共同設計の方法名を `Architecturing` とし、README でその意図を説明する。
- 既存の `design-doc` スキルを `architecturing` に改名し、設計の成果物は Design Doc のままにする。
- 重要な設計判断はエンジニアが担い、双方が発案・修正できる関係を維持する。
- AI が迎合せず、前提や案を検討する。
- エンジニアが自分の考えを持ち寄る姿勢を説明し、毎回の質問や意見の事前提出、固定の発言順は求めない。
- 自身の仮説・理由・迷いを考え、持ち寄れるよう、AI が必要に応じて支援する。
- 未整理の意見や違和感も共同設計の材料として扱い、考える手掛かりが必要なら関連する事実や論点を示す。
- 新規 Draft の作成時に、AI が仮案などを書き込まないよう指示する。
- 既存の設計ループのフェーズ構成、責務、承認境界を維持する。
- `Architecture Exploration` を含む既存のフェーズ名は変更しない。

## 対象外

- 同じ共同設計を担う別スキルの追加。
- ワークフロー外の単独利用のための開始条件・終了条件の新設。
- 実行中の別案件や、インストール済みスキルへの直接変更。

## 完了条件

- README から、Architecturing の意味、Design Doc との関係、双方の参加の仕方が読める。
- 新名称と関連する参照が整合し、既存の責務と成果物が保たれる。
- Draft 作成時の指示が、仮案を書き込まない方針として整合している。
- エンジニアの思考を支える AI の振る舞いが説明され、意見の事前提出などの新たな開始・承認条件が追加されていない。
- AI が迎合せず、前提や案を検討する方針が説明されている。

## 設計で整理すること

新名称への参照の整理、README とスキルが説明する内容、共同設計を支援する AI の振る舞い、初期 Draft に記載する
内容の境界と既存の探索・執筆ガイドとの整合を、Design Doc で扱う。
ここで未検討の実現案や、既存スキルの暫定案を採用済みの条件として追加しない。
