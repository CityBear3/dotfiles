## Context and scope

エンジニアと AI が Design Doc を軸に構造を共有し、共同で設計を
組み立てる進め方を Architecturing と呼ぶ。構造が共同で作り上げられて
いくという意図を、この名前に込める。

双方が仮説や別案を持ち寄り、システムの構造と、それを説明する文書の
構造を考える。エンジニアは自身の考えや違和感を伝え、重要な設計判断を担う。

今回は、Design Doc を成果物とする既存の design-doc スキルの改名と、
README への説明追加を扱う。併せて、Draft 作成時に仮案などを書き込まない
方針と、エンジニアが自身の考えを持ち寄れるよう AI が支援する方針を追加する。
共同設計への参加を、エンジニア側の心構えだけに依存させず、AI の振る舞いとして支える。

入力の詳細は
[要件](../requirements/2026-11-05-codex-architecturing/requirements.md)
を参照する。

### Goals

- Architecturing の意味と、双方の参加の仕方を説明する。
- 既存スキルの責務と成果物を維持して改名する。
- Draft 作成時に仮案を書き込まない方針を明確にする。
- エンジニアが自身の考えを持ち寄れるよう支援する AI の振る舞いを定義する。
- AI が迎合せず、前提や案を検討する方針を明確にする。

### Non-goals

- 同じ共同設計を担う別スキルの追加。
- ワークフロー外の単独利用に向けた手順の新設。
- 設計ループのフェーズ構成や承認境界の変更。

## Overview

既存の `design-doc` スキルを `architecturing` に改名し、Design Doc を軸に
エンジニアと AI が構造を共同で作り上げる方法として位置づける。
README では、Architecturing の定義と命名の意図を説明する。

共同設計への参加を AI の振る舞いとして支えるため、迎合せずに前提や案を
検討すること、エンジニアが自身の考えを持ち寄れるよう支援すること、
毎回の質問や事前提出を義務化しないことを基本方針とする。
重要な設計判断はエンジニアが担う。

Draft は構造の探索や検証の結果を整理する文書とし、作成時に仮案や
未整理の意見を書き込まない。それらは設計ループの中で扱う。

既存のフェーズ名、スキルの責務、実装の委任範囲と承認境界は維持する。
質問の常態化や実装の自律性への懸念は、既存の規則と今回の三原則を
抑制の仕組みとして許容し、追加対策は設けない。

## Detailed design

設計を共同で構造化するスキルの構成として重要な点として、

- この構造を共同で作り上げる意図を含むスキル名にし、このスキルの考え方を自然と扱えるようにする
- 共同で構造化するために、エンジニアが能動的に設計に参加できるように支援し、受け身にならないようにする

があり、この文章ではこれらを明確化する。

### 名称と既存の責務

共同設計の方法名を `Architecturing`、それを支援するスキル名を `architecturing`
とする。成果物や作業状態の呼び名は、方法名と区別する。

| 対象 | 名称 | 表すもの |
| --- | --- | --- |
| 共同設計の方法 | Architecturing | エンジニアと AI が設計を組み立てる営み |
| スキル | `architecturing` | その進め方を支援する既存スキルの新名称 |
| 設計の成果物 | Design Doc | 構造・挙動・設計理由を共有する文書 |
| 文書の作業状態 | Draft | 設計を組み立てている途中の状態 |

構造を共同で作り上げていく感覚を名前にも込めるため、あえて `turing` を含む
`Architecturing` という綴りを採用する。README では、この定義と命名の意図を説明する。

既存の `design-doc` スキルを `architecturing` に改名し、構造の探索、検証、
Design Doc の共同執筆・最終化、承認後の Feature Contract 導出という責務を引き継ぐ。
`Architecture Exploration` を含む既存のフェーズ名は変更しない。
フェーズ名は段階を、Architecturing はその段階で用いる共同設計の方法を表す。

### 共同設計を支える AI の振る舞い

共同設計では、次の三点を基本方針とする。

- AIが迎合せず、前提や案を検討する
- エンジニアが自分の考えを持ち寄れるよう支援する
- 毎回の質問や事前提出を義務化しない

エンジニアが最初から能動的に参加することだけに依存せず、共同設計に
参加しやすくなる支援を、スキルが AI に求める振る舞いとして定義する。

エンジニアが、AIに案や評価を求める際にも自身の仮説・理由・迷いを考え、持ち寄れるよう支援する。必要に応じて現在の考えを尋ね、未整理の意見や違和感も共同設計の材料として扱う。考える手掛かりが必要なら、関連する事実や論点を示す。意見の事前提出や固定の発言順は求めない。

この仕組みが整えるのは、エンジニアが考えを持ち寄りやすくなる機会と支援である。
自発的な思考や理解そのものを保証するものではなく、意見が出たことや同意が
得られたことだけで、その姿勢が実現したとは判断しない。

明文化によって AI が毎回意見を尋ねるようになると、思考や対話を型にはめる
おそれがある。「必要に応じた支援」とすることで、その過剰な運用を避ける。


### Draft 作成時に記載する内容

Design Doc の Draft 作成時には、仮案や未整理の意見を記載しない。Draft は、構造の探索や検証の結果を整理した文書であり、未整理の意見は設計ループの中で扱う。

## Cross-cutting concerns

### 質問の常態化と実装の自律性への影響

思考を支援する指示が毎回質問する手順として解釈されることや、設計中の協働の
進め方が実装にも一律に適用され、局所的な実装判断ごとに確認が必要になることを懸念する。

質問の常態化に対しては、既存の設計スキルに、質問回数や毎回質問で終えることを
要求しない規則がある。今回の三原則にも「毎回の質問や事前提出を義務化しない」
と明記し、思考支援を必要に応じたものとしている。

実装の自律性に対しては、既存の
[ワークフロー](../../codex/skills/agentic-engineering-workflow/SKILL.md#continue-within-authority)
が、承認済み範囲の実装・検証・修正を繰り返し承認を求めず進める方針を持つ。
また、[実装スキル](../../codex/skills/execute-task/SKILL.md#implement-and-commit-locally)
は、委任範囲内のファイル、ヘルパー、局所的な型やアルゴリズムなどの選択を実装側に任せている。
本変更でも、この委任範囲と承認境界を維持する。

懸念は残るものの、既存の規則と今回の三原則によって抑制する仕組みがあるため、
許容できると判断する。これらの仕組みを維持し、今回のための追加対策は設けない。

## Alternatives considered

### Architecting とする

方法名を `Architecting`、スキル名を `architecting` とする案も検討した。
設計する行為を表す名前として候補となる。

今回は、構造を共同で作り上げていく感覚を名前にも込めることを重視し、
あえて `turing` を含む `Architecturing` を選ぶ。名前だけではその意図が
伝わりきらないため、README で定義と命名理由を説明する。

### 具体的な支援方針を追加しない

既存の共同設計の原則に委ね、仮説や迷いを尋ねるといった行動を追加で規定しない。
指示を簡潔に保ち、状況に応じた対話の裁量を残せる。追記がないこと自体が、
エンジニアの思考や発案を制限するわけではない。

一方、いつ、どのように思考を支援するかは、AI の解釈や参加者の働きかけに
委ねられる。今回は、支援する行動を AI への指示として明確にすることを選ぶ。
意見の事前提出や固定の発言順を求めず、対話の裁量も維持する。
